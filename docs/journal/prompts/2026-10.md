  **Findings**

  1. **High: a replayed GRANT turns consent on with no consent record.** Files: `application/use_cases/learners.py:71-72` and `research/erasures.py:45-50`.
     - GRANT is written to the log before commit. If the commit then fails, the log says "granted" but the user never actually consented.
     - After a restore, the backup has no `consent_records` row for that grant. Reapply still sets `research_consent=True`, so the bot starts recording voices with no evidence of consent.
     - Fix: write the log entry before commit only for WITHDRAW and DELETE. Write GRANT after commit, so a failed write fails safe.
     - In reapply, set consent to True only if `consent_records` has a granted row with `at >= entry.at`. Otherwise leave it False and the learner consents again.

  2. **Medium: the `./data/erasures` bind mount in `docker-compose.yml` breaks on Linux.**
     - If the host folder is missing, Docker creates it owned by root. The bot runs as uid 10001, so `record()` raises PermissionError before commit.
     - Result: "Delete my data" and consent withdrawal both stop working.
     - The other way round, the 0600 file owned by 10001 can't be read by the host's `reapply-erasures` or by `backup.sh`'s `cp`. Docker Desktop on macOS hides both problems.
     - Fix: create `data/erasures` with the right owner in setup or `roles.sh`, or add a startup write check.

  3. **Low: reapply bypasses the use cases and its counts mislead.** File: `research/erasures.py:41-53`.
     - It updates `learners` directly and records no `consent_changed` or `learner_deleted` events, so the events table disagrees with the consent state after a replay.
     - Withdraw and grant entries are counted on every run, even when nothing changes, so a second run still reports changes. Count only real changes, for example via rowcount or a before/after consent check.

  4. **Low: conftest has no isolation between parallel runs.** File: `tests/integration/conftest.py:26-40`.
