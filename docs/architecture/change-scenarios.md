# Можно ли менять архитектуру: сценарии изменений и проверка (2026-10-18)

Вопрос автора: «чтоб была возможность изменять что-то в ней и чтоб работало нормально». Ответ — по фактам:
что держит архитектуру, сколько файлов трогает типичная замена, где слабые места.

## Что держит архитектуру сейчас
| Что | Чем проверено | Результат 2026-10-18 |
|---|---|---|
| Слои domain → application → infrastructure / presentation → bootstrap | import-linter, 5 контрактов (`pyproject.toml`) | 5 kept, 0 broken |
| Домен без фреймворков и ввода-вывода | контракт «Домен чистый» | держится |
| Вся склейка в одном месте | `bootstrap/di.py`; тест: каждый сценарий зарегистрирован | держится |
| Типы | mypy --strict, 134 файла (143 после ADR-0049) | без ошибок |
| Поведение | `make check`: 658 тестов до ADR-0049, 699 после; покрытие 97,5 % | зелёный |

## Пробная замена: другая модель распознавания
Сделана в отдельной копии репозитория и удалена после проверки. Новый класс `DrillRecognizer`
(«слышит» эталон без последней фонемы) закрывает порт `PronunciationRecognizer`.

| Файл | Правка |
|---|---|
| `infrastructure/asr/drill.py` | новый адаптер, 9 строк |
| `bootstrap/config.py` | `asr_backend: Literal[..., "drill"]` |
| `bootstrap/di.py` | ветка `if asr_backend == "drill"` |

Итог: import-linter — 5 из 5 контрактов; тесты — 649 passed (как без правки); контейнер DI с
`ASR_BACKEND=drill` отдаёт `DrillRecognizer`, попытка получает `model_version = "drill"`.
Сценарии, оценка, БД, Telegram, отчёты не тронуты. Так же подключается Whisper или своя модель (докторантура).

## Другие сценарии (по коду, без пробной замены)
| Замена | Что трогать | Почему так мало | Риск |
|---|---|---|---|
| PostgreSQL ↔ SQLite | только `DATABASE_URL` | тесты идут на SQLite, прод — на PostgreSQL, репозитории общие (SQLAlchemy Core) | различия диалектов: `tests/integration/test_postgres.py` пропускается без `TEST_POSTGRES_URL` |
| Telegram → веб или другой мессенджер | новая папка `presentation/<канал>/` + точка входа | сценарии в `application/use_cases/` не знают об aiogram (контракт) | экраны (`screens.py`, `render.py`) придётся повторить |
| Язык объяснений | `curriculum/lexicon.<код>.yaml`, `feedback.<код>.yaml` | тексты ошибок — данные, а не код | только человек (контент) |
| Пороги «засчитано / отлично» | `domain/policy.py` или `PASS_THRESHOLD` | одно место, пишется в каждую попытку | только человек (методика) |

## Слабые места — найдены и исправлены (ADR-0049)
| Где было | Что | Как исправлено |
|---|---|---|
| `handlers.py`, `annotation.py` | 7 словарей на уровне модуля хранили состояние разговора; тест показал «протекание» эталона между двумя ботами | состояние разговора — в FSM aiogram (`Desk` у разметчика, ключ `recording` у учителя); кэш экранов — `Display` из DI; тест запрещает изменяемое состояние на уровне модулей |
| `handlers.py` (553 строки) | все обработчики ученика в одном файле | пакет `handlers/`: `commands`, `navigation`, `data`, `reference`, `voice` (≤ 250 строк, проверяет тест); перехват сбоев — `errors.py` |
| CI | Docker-образ не собирался | job `docker`: сборка образа, импорт кода и права на `/app/data` в нём |

Осталось (TD-FN-70): состояние разговора пропадает при перезапуске — постоянное хранилище FSM после пилота.

## Как держать это дальше
- Новая внешняя система — только через порт и адаптер (CLAUDE.md); нарушение роняет `make check`.
- Перед крупной правкой — `solution-architect`, после — `architecture-guardian` и `direction-reviewer` (ADR-0047).
