## 1. Цель продукта

Создать спокойный, понятный русскоязычному взрослому новичку путь обучения чтению арабского по «Аль-Муаллим ас-Сани».

Цель первой версии по материалам проекта:
- ограниченный законченный учебный срез — уроки 1–3;
- фокус Этапа I — буквы и огласовки (в проектных документах фигурирует цель 28 пунктов/букв; точное соответствие учебной программе должно быть подтверждено владельцем);
- короткое видео преподавателя (до 5 минут, 1–3 буквы);
- изображение со словами урока и эталонное аудио живого человека;
- голосовая попытка ученика в Telegram;
- дружелюбный разбор текстом или изображением;
- общий и внутрисессионный прогресс;
- серия занятий как поддержка, не наказание;
- большая веха после освоения всех 28 пунктов и переход к Этапу II.

Принцип интерфейса: **одно основное действие на экран, минимум когнитивной нагрузки**. Не превращать продукт в копию Duolingo с множеством игровых механик.

## 2. Неприкосновенные ограничения

### Учебная методика и контент
- Не добавлять кириллическую транслитерацию на экраны ученика.
- Не генерировать AI-голос для эталонного произношения.
- Не генерировать AI-картинки/AI-видео для учебного содержания.
- Эталонное аудио — только подтверждённые человеческие записи из источников проекта.
- Видео — реальный преподаватель; арабская речь и русские субтитры, согласно требованиям проекта.
- Порядок — строго по утверждённой книге/программе.
- Арабские буквы, огласовки, примеры слов, переводы, объяснения артикуляции и тексты ученику нельзя сочинять или молча исправлять.
- Не менять пороги, правила зачёта, классификацию ошибок, `MOSHAF_PARAMS`, методику и содержимое `curriculum/` без явного решения владельца.
- Ошибка произношения не должна унижать ученика или превращаться в блокировку дальнейшего обучения. Но не менять существующие правила «засчитано» без согласования: в документах есть противоречие между мягким прохождением и текущими M-01/M-02/M-12.

### Архитектура и безопасность
- Сохранять Python 3.12, aiogram 3, PostgreSQL и слои domain / application / infrastructure / presentation.
- Widget — только presentation. Не переносить учебные правила и оценивание в JavaScript.
- Состояние урока и прогресс авторитетно хранить на сервере.
- Данные из `widget_query` считать недоверенными; проверять формат, длину, пользователя, чат, сообщение и допустимый переход.
- Не класть секреты, токены, идентификаторы учеников и приватные данные в HTML или `public_data`.
- Не читать `.env`, `data/`, дампы БД и реальные голосовые записи без прямой необходимости и разрешения.
- Не менять схему БД и не добавлять зависимости без согласования.
- Не коммитить и не пушить без предусмотренного проектом процесса `/ship` и подтверждения владельца.

## 3. Важная методическая неоднозначность — не решать самостоятельно

В `spec-for-chatgpt.md` написано «один урок — пять шагов», таблица пути содержит шаги 1–5, но в других местах шапка интерфейса обозначена как «шаг k из 4», а в HTML `lesson.html` прогресс тоже построен на четырёх шагах/экранах.

До реализации:
1. Зафиксируй противоречие в отчёте.
2. Предложи два варианта: единая модель из 4 шагов (если прогресс объединяется с разбором) или 5 шагов (если прогресс — отдельный этап).
3. Не выбирай молча. Спроси владельца, если решение влияет на пользовательский текст, аналитику или состояние урока.
4. В коде не создавать параллельные несовместимые счётчики шагов.

Также подтвердить у владельца:
- что именно означает «28»: 28 букв, 28 учебных пунктов или 28 букв с огласовками;
- как уроки 1–3 отображаются на эти 28 пунктов;
- какие видео, картинки и эталонные аудио уже подтверждены;
- что считается минимальным завершением урока и как это соотносится с `M-01`, `M-02`, `M-12`.

## 4. Визуальная система

Смотри концепт `design/muallim-2.0-eight-screens.png`. Он показывает направление, не финальную спецификацию контента.

### Стиль
- Основа: тёплый кремовый фон, тёмно-зелёный основной цвет, мягкий шалфейный для вторичных состояний, золото только как акцент.
- Спокойная исламская геометрия/растительные мотивы по краям; не перегружать орнаментом.
- Высокая читаемость, крупный арабский текст с огласовками.
- Использовать доступный системный стек шрифтов. Не загружать внешние шрифты внутрь Telegram Widget.
- Карточки с мягкими границами и умеренным радиусом; единая сетка и интервалы.
- Поддержать тему Telegram; не полагаться только на жёстко заданные цвета.
- Контраст и размер интерактивных целей должны быть удобны взрослым новичкам.
- Декор никогда не должен мешать арабским буквам, огласовкам, словам или кнопкам.

### Предварительные дизайн-токены (ориентир, адаптировать к Telegram theme)
- page background: `#FFF8EA` / theme-aware equivalent;
- primary green: `#176B3A`;
- dark green: `#124B2D`;
- soft green: `#E5F0D8`;
- gold accent: `#D9A83F`;
- body text: `#17231B`;
- muted text: `#6F756D`;
- card border: warm beige `#E9DCC4`.
Это визуальные предложения, не учебные решения.

## 5. Информационная архитектура и экраны

Не обязательно делать каждый экран отдельным Telegram Widget-сообщением. Сначала изучи актуальный API и текущий UX бота. Используй минимальное количество сообщений и не дублируй действия.

### A. Главный экран — «Муаллим»
Содержимое:
- название и краткое назначение;
- Этап I: буквы и огласовки;
- серверный прогресс по программе (например, `n / 28`, только если владелец подтвердит семантику 28);
- одна главная кнопка «Продолжить урок»;
- вторичные переходы «Карта букв» и «Прогресс».

Не показывать несколько конкурирующих CTA. Не выводить фальшивые проценты/статистику.

### B. Шаг 1 — видео
- заголовок «Урок N · шаг 1» (формат шага согласовать);
- видео преподавателя не длиннее 5 минут и покрывающее 1–3 буквы;
- подпись с темой/длительностью;
- действие «Видео просмотрено» или «Дальше» — только если это соответствует фактическому UX Telegram.
Видео отправляется обычным сообщением Telegram, не HTML Widget. Виджет может быть отдельной карточкой-навигацией, если это реально улучшает UX.

### C. Шаг 2 — слова и эталонное произношение
- одна утверждённая картинка со словами урока либо аккуратно оформленная карточка;
- арабское написание с огласовками;
- эталонная запись живого человека отправляется отдельным аудиосообщением/файлом Telegram;
- никакой встроенной HTML-аудиоплеерной имитации: профиль Widget из проектного исследования не поддерживает `<audio>`.
- если аудио привязано к каждому слову, показать это в понятной последовательности обычных сообщений/кнопок Telegram, не имитируя неподдерживаемое поведение.

### D. Шаг 3 — попытка ученика
- короткая инструкция: прочитать слова и отправить голосовое сообщение боту;
- запись выполняется стандартным интерфейсом Telegram, а не микрофоном внутри Widget;
- Widget не запрашивает микрофон и не показывает фиктивный статус «записывается»;
- предусмотреть текстовую подсказку, как отправить voice message, и обработку неправильного типа вложения.

### E. Шаг 4 — разбор
- результат распознавания из существующего backend;
- 1–3 приоритетных замечания в дружелюбной формулировке, только если backend действительно их вернул;
- подсветка соответствующих фрагментов, если точная привязка существует;
- две понятные опции: «Повторить» и «Следующий урок» (если они разрешены методикой);
- не показывать выдуманный нулевой счётчик ошибок;
- не заявлять «идеально» при неполной/неуверенной оценке.

### F. Карта букв
- сетка из утверждённых 28 пунктов программы;
- состояния: изучено / текущий пункт / доступно позже — только если это соответствует правилам курса;
- возможность повторить пройденный пункт, если это поддерживается backend;
- данные и порядок приходят с сервера, не дублируются вручную в JS;
- не зашивать непроверенный список букв в нескольких местах.

### G. Прогресс
Показывать только метрики, которые реально существуют и корректно вычисляются:
- прогресс по учебной программе;
- завершённые уроки;
- серия занятий (если текущая модель её поддерживает).
Серия — мотивация, не наказание. Не обнулять и не стыдить ученика текстами.

### H. Большая веха
- показывать только при реальном завершении утверждённой цели 28/28;
- поздравление и краткая статистика из реальных данных;
- CTA «Перейти к Этапу II» только если Этап II существует/разрешён в продукте;
- не использовать кнопку «Поделиться», если Telegram Widget/production ограничения не обеспечивают её корректную работу.

## 6. Telegram Widgets — обязательная техническая проверка до кода

Файл `docs/research/telegram-widgets.md` содержит исследовательские заметки на 2026-11-15, но их нельзя считать вечной истиной. **Claude обязан заново проверить официальные документы Telegram на момент реализации** и зафиксировать дату/ссылки/результат.

Проверить как минимум:
- актуальный Bot API и changelog;
- официальный Widgets guide и профиль HTML/CSS/JS;
- реальные методы отправки, редактирования данных и ответа на widget query;
- типы Update и `allowed_updates`;
- production vs test server ограничения;
- поддерживаемые Telegram-клиенты и минимальные версии;
- HTML-валидатор и точные лимиты;
- поведение caption/fallback на клиентах без поддержки;
- что именно умеет текущая версия aiogram, а что нет.

Не предполагать, что `sendWidget` доступен в установленном aiogram. Не обновлять aiogram и не добавлять библиотеку автоматически. Если поддержки нет, подготовить варианты реализации через тонкий адаптер/сырой API и показать плюсы/минусы владельцу согласно `PROJECT-RULES.md`.

### Ограничения прототипов из исследовательского файла — перепроверить
Согласно текущим заметкам проекта, Widget:
- не является Mini App;
- не имеет fetch/network, `<audio>`, `<video>`, микрофона и текстового ввода;
- имеет очень жёсткий размер HTML и сжатого payload;
- получает состояние от бота, а не сохраняет авторитетное состояние сам;
- может отправлять ограниченные запросы по явному действию пользователя;
- может обрезать содержимое при превышении высоты;
- должен иметь fallback-подпись для старых клиентов.
Проверь каждое утверждение по официальному источнику, не копируй его автоматически.

### Проверка HTML
Для каждого файла:
- профиль разрешённых тегов, CSS и JS;
- отсутствие внешних ресурсов;
- размер исходного HTML и точный `zlib.compress(html.encode("utf-8"), 9)`;
- лимит данных в байтах, а не символах;
- отсутствие неподдерживаемых API;
- обработка `TelegramWidget === undefined`;
- корректный первый синхронный рендер;
- безопасная обработка `chatData/publicData`;
- проверка ошибок и таймаутов;
- мобильная ширина, включая узкий экран;
- высота виджета и нижняя зона времени сообщения;
- тапы/горизонтальные жесты/системная зона назад;
- reduced motion и тема Telegram;
- отсутствие критичных действий, доступных только через hover.

## 8. Архитектурные правила внедрения

Соблюдай текущую карту проекта из `PROJECT-RULES.md` и `docs/architecture/overview.md`.

Ожидаемое разделение:
- `domain`: правила обучения/оценки, никаких Telegram типов;
- `application`: use cases и ports;
- `infrastructure`: Telegram API adapter, БД, файлы, Muaalem;
- `presentation/telegram`: handlers, widget rendering, Telegram-specific DTOs/views;
- `bootstrap/di.py`: регистрация зависимостей и сценариев.

Widget HTML — статический presentation artifact. Не помещать в него:
- оценивание произношения;
- порядок учебной программы как единственный источник истины;
- пороги зачёта;
- пользовательские идентификаторы/секреты;
- генерацию учебного контента.

Состояние должно иметь версию схемы, например `v`, и минимальный набор полей. Конкретную схему предложить в аудите; не вводить её без согласования.

## 9. Критерии приёмки вертикального среза

### Функциональные
- Ученик может начать и продолжить один урок.
- Видео, слова и эталонный звук отправляются реальными Telegram-сообщениями.
- Голосовое принимается штатным Telegram handler.
- Оценка вызывается существующим application use case.
- Результат соответствует реальному ответу backend.
- Ученик может продолжить по утверждённой методике.
- Повторное открытие не теряет состояние.
- Данные одного пользователя не смешиваются с данными другого.

### Виджет
- Валидный HTML-профиль Telegram.
- В пределах всех лимитов.
- Нет внешних сетевых запросов/ресурсов.
- Работает с тёмной и светлой темой.
- Корректен при отсутствии `TelegramWidget`.
- Все запросы валидируются сервером.
- Каждый query получает ответ даже при ошибке.
- Понятный fallback для старых клиентов.

### Качество
- Unit tests для преобразования состояния и контрактов.
- Handler tests для widget query и voice message.
- Тесты ошибок/таймаутов/дубликатов/чужих сообщений.
- Проверка архитектурных границ import-linter.
- Точечные проверки изменённых файлов.
- Полный `make check` — только по просьбе владельца согласно правилам проекта.

## 10. Что не делать

- Не переписывать весь бот ради нового интерфейса.
- Не делать сразу все четыре виджета production-ready до проверки одного урока.
- Не заменять Telegram voice message фальшивым микрофоном внутри Widget.
- Не помещать аудиоплеер/видеоплеер в HTML Widget без подтверждения официального профиля.
- Не зашивать список букв/словарь в HTML.
- Не добавлять искусственные достижения, проценты, streak или результаты.
- Не менять учебную последовательность и содержание.
- Не менять пороги и классификацию ошибок.
- Не делать миграцию БД «на всякий случай».
- Не обновлять aiogram/зависимости автоматически.
- Не заявлять, что API поддерживается, пока это не проверено на актуальной версии и тестовом сервере.
- Не использовать прототипное изображение как источник арабского учебного текста: изображения — только визуальный ориентир.

## 11. Формат отчёта Claude после каждой фазы

Используй формат:

1. **Статус:** завершено / заблокировано / нужно решение.
2. **Что проверено:** команды, документы, тесты, официальные источники.
3. **Что изменено:** список файлов и краткое назначение.
4. **Что не менялось:** особенно методика, curriculum, БД, зависимости.
5. **Результаты тестов:** точные команды и итоги.
6. **Риски/открытые вопросы:** без догадок.
7. **Следующий шаг:** один конкретный шаг.
8. **Нужны ли решения владельца:** сформулировать вопрос с 2–4 вариантами.

Начни с Фазы 0. Не пиши код до завершения аудита и согласования открытых продуктовых решений.
