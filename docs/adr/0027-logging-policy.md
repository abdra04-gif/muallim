# ADR-0027: Логи — stdout с ротацией, без персональных данных и секретов, правила проверяет тест

- **Статус:** Принято
- **Дата:** 2026-10-17
- **Кто решил:** предложил агент; автор поручил выбрать лучший вариант («проанализируй и дай лучшее решение»)
- **Связано:** NFR-SEC-01, NFR-SEC-02, NFR-REL-02, ADR-0010, ADR-0015, TD-SEC-04, TD-SEC-08, TD-FN-21, R-C4; идея — ADR-0014 проекта-калькулятора, где команда записала свою стратегию логирования

## Контекст
В боте голоса и псевдонимы учеников. Логи — это ещё одно место, куда могут попасть персональные данные,
и его легко забыть: логи не выгружаются, не удаляются по `/delete` (FR-10) и не попадают в план хранения.
Что было до решения:

| Где | Что нашли |
|---|---|
| `bootstrap/main.py` | `logging.basicConfig` в stderr, уровень из `LOG_LEVEL` |
| `presentation/telegram/handlers.py` | при сбое распознавания пишется **псевдоним** и traceback; Telegram ID нигде не пишется |
| aiogram | «Update id=… handled … by bot id=…» — номер апдейта и ID бота, ученика нет |
| Quran Muaalem | `logging.info("mismatch Level")` в корневой логгер на каждую запись (TD-FN-21) |
| сетевые библиотеки | на `DEBUG` могут напечатать URL запроса, а в URL Telegram — **токен бота** (`/bot<токен>/…`) |
| `docker-compose.yml` | **ротации нет**: логи растут без предела, и срок хранения ничем не ограничен (TD-SEC-08) |

Правило, записанное только в документе, не держится: агент пишет большую часть кода (R-15).
Значит, правило должен проверять тест, как уже сделано для слоёв (ADR-0002).

## Решение
1. **Куда:** стандартный `logging` → stdout → драйвер Docker `json-file` с ротацией **3 × 10 МБ** на сервис.
   Срок хранения ограничен объёмом; отдельных файлов логов в `data/` нет.
2. **Что можно:** технические события, псевдоним ученика (`L-…`), ID попытки и карточки, длительности,
   имена исключений и traceback.
3. **Что нельзя:** Telegram ID, имя и username, текст сообщений и подписей, голос (байты, пути),
   услышанные фонемы, токен, строка подключения к БД. Псевдоним можно, потому что связь с человеком
   хранится только в БД (ADR-0010). Фонемы нельзя: это данные исследования, они живут в БД по правилам согласия.
4. **События для исследования** (сбой распознавания, жалоба и т. п.) пишутся в `interaction_events`, а не в лог.
   Лог служит для диагностики и не является источником данных диссертации.
5. **Настройка в одном месте:** `bootstrap/logs.py::configure_logging`. На обработчике стоят два фильтра,
   поэтому они видят и чужие библиотеки:
   - `RedactSecrets` маскирует токен бота (и внутри URL), пароли в URL и явно переданные секреты,
     в тексте и в traceback;
   - `DropLibraryNoise` отбрасывает INFO-шум Muaalem, а предупреждения и ошибки оставляет (закрывает TD-FN-21).
6. **Уровень:** `INFO` в пилоте. `DEBUG` — только локально, при разработке.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **stdout + ротация Docker + запреты, проверяемые тестом + фильтр секретов** | без новых зависимостей; правило нельзя нарушить незаметно; срок хранения ограничен; закрывает шум Muaalem | AST-тест ловит запрещённые **имена** переменных, а не смысл: значение под другим именем пройдёт (страхует ревью) | **выбран** |
| Только правило в документе | ничего не писать | не держится при агентной разработке (R-15); токен на DEBUG не защищён | отклонён |
| JSON-логи (structlog) | удобный поиск и машинный разбор | новая зависимость; один процесс на ноутбуке, разбирать логи машиной незачем | отклонён (вернуться при T3: несколько серверов) |
| Таблица логов в PostgreSQL | всё в одном месте, SQL-поиск | дублирует `interaction_events`; логи с traceback попадают в бэкапы (TD-SEC-17) и могут уйти в выгрузки | отклонён |
| Файлы логов в `data/logs/` | логи переживают пересоздание контейнера | ещё одно место с данными; ротацию и удаление писать самим | отклонён |
| Внешний сервис (Sentry и т. п.) | алерты, группировка ошибок | данные уходят за границу (TD-SEC-04); ещё один обработчик ПДн | отклонён (до решения OQ-08) |

## Последствия
- Новый `logger.*(...)` с запрещённым именем в аргументах роняет `make check` и CI.
- `logging.basicConfig` в обход `configure_logging` тоже роняет тест.
- Псевдоним в логе связывает сбой с попытками ученика. После `/delete` его строки в логах остаются
  до ротации (≤ 30 МБ). По псевдониму без БД человека не найти; это записано в `security/privacy.md`.
- `docker logs` хранит только последние ~30 МБ: старые сбои пропадают. Для диссертации это не важно,
  потому что доля сбоев считается по `interaction_events` (NFR-REL-02).

## Как проверить
- `tests/architecture/test_logging.py`: запрещённые имена в вызовах логгера, единственное место настройки,
  ротация в `docker-compose.yml`.
- `tests/unit/test_logs.py`: маскирование токена (в том числе внутри URL), пароля в URL и traceback;
  отбрасывание шума Muaalem; фильтры работают на настроенном обработчике.
