# ADR-0054: Три входа в БД, журнал удалений вне БД, проверка на настоящем PostgreSQL

- **Статус:** Принято
- **Дата:** 2026-10-20
- **Кто решил:** автор (три входа, журнал удалений, копии по расписанию — позже, без ловушек для
  разметчиков); реализацию предложил агент
- **Связано:** FR-10, NFR-TR-03, NFR-SEC-01, ADR-0040, TD-DB-01, TD-DB-03, TD-DB-05, TD-DB-08, TD-FN-14, TD-SEC-11

## Контекст
После ADR-0040 оставались решения человека: бот и DBeaver входили в PostgreSQL суперпользователем
(одна ошибка или клик — и данных нет); восстановление старой копии возвращало учеников, удаливших
данные позже (152-ФЗ); контейнер бота применял миграции при каждом старте без копии. Все тесты, кроме
одного, шли только на SQLite — на PostgreSQL проверялись лишь миграции и отчёты.

## Решение
- **Три роли PostgreSQL** (`scripts/db/roles.sql`, `make db-roles`, повторный запуск = смена паролей):
  `muallim_owner` — владелец таблиц, только он меняет схему (миграции, `MIGRATION_DATABASE_URL`);
  `muallim_app` — бот и `muallim-research`: читать и писать строки, схему не трогать;
  `muallim_reader` — DBeaver: только чтение (`default_transaction_read_only`), Telegram ID и коды
  приглашений скрыты. Ни одна роль не суперпользователь; `PUBLIC` не входит в базу и не создаёт
  объекты. Таблицы, созданные позже владельцем, получают права автоматически (default privileges).
- **Миграции не при старте контейнера**: `CMD ["muallim"]`; применяет человек — `make migrate`.
- **Копия перед миграцией — только БД** (`backup.sh --db-only`): замер на 50 000 попыток — база 43 МБ,
  копия 0,5 с (3,2 МБ), проверка 0,08 с. Записи миграции не трогают; полная копия — `make backup`.
- **Журнал удалений вне БД** (`data/erasures/erasures.jsonl`, рядом с записями): «удалить», «отозвал
  согласие», «снова дал согласие» + UUID ученика (без Telegram ID). Удаление и отзыв пишутся **до**
  commit (намерение не теряется), согласие — **после** (журнал не утверждает согласия, которого нет в
  БД). Копия сохраняет журнал; восстановление **объединяет** журналы копии и текущий и сразу повторяет
  (`muallim-research reapply-erasures`). Повтор включает согласие, только если в БД есть запись о нём
  позже отзыва; иначе ученик даёт согласие заново. Оборванная последняя строка (сбой посреди записи)
  пропускается. `verify` показывает неприменённые удаления.
- **Бот в Docker не получает чужих паролей**: суперпользователя, владельца и просмотра (обнулены в
  `docker-compose.yml`). Пароли ролей `roles.sh` передаёт psql через stdin, не аргументами.
- **Восстановление на новом сервере** требует ролей: `restore.sh` проверяет их до `pg_restore`.
- **Весь интеграционный набор — и на PostgreSQL**: при `TEST_POSTGRES_URL` (в CI задан) фикстура
  сессии идёт на настоящий сервер; на PostgreSQL сверяется схема с миграциями.

## Рассмотренные варианты
| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Бот «только записывает» без DELETE | буквально как сказал автор | «Удалить мои данные» и отзыв согласия перестанут работать (FR-10) | отклонено; DELETE строк есть, TRUNCATE и DDL — нет |
| Просмотр — только представления `v_*` | меньше видно | отчёты `analytics/sql` читают таблицы | отклонено; таблицы видны, Telegram ID — нет |
| Роли в миграции Alembic | всё в одном месте | пароли в коде или окружении миграций; роли — на весь сервер | отклонено |
| Журнал удалений в БД | проще | восстановление старой копии стирает и журнал | отклонено |
| Повтор журнала только с даты копии | меньше работы | дату копии легко перепутать | отклонено: журнал повторяется целиком, результат тот же |
| Копия по расписанию и вне ноутбука | защита от потери ноутбука | нужен выбор места и шифрования | отложено автором (TD-FN-14) |
| Скрытая слепая выборка для проверки разметчиков (TD-DB-08) | ловит «согласие по подсказке» | автор доверяет разметчикам | отклонено автором 2026-10-20; слепая разметка **тестовой** части по предрегистрации — отдельное решение, не тронуто |

## Решения автора по вопросам ревью (2026-10-20: «делай как сам знаешь»)
- Боту оставлено право DELETE строк — без него не работают «Удалить мои данные» и отзыв согласия.
- Перед миграцией копируется только БД; полная копия с записями — `make backup`.
- Текст ученику после отзыва — «прежние **будут** удалены»: основные записи удаляются сразу, копии в
  пакетах разметки и выгрузках удаляет исследователь по `verify` — обещать «удалены» было бы неточно.

## Последствия
- Журнал лежит на том же диске, что и база: при потере диска пропадут удаления после последней копии,
  вынесенной с компьютера — закрывается вместе с копиями вне ноутбука (TD-FN-14).
- Повтор журнала не пишет событий в `interaction_events`; Linux: папки `data/audio`, `data/erasures`
  для контейнера (uid 10001) — TD-DB-10.
- Перед пилотом: `make db-roles` один раз (пароли в `.env`), DBeaver — пользователь `muallim_reader`.
- После миграции с новой колонкой Telegram ID — снова `make db-roles` (тест проверяет, что ID скрыт).
- Восстановление на новом сервере: сначала `make db-roles` (роли — на весь сервер, в дампе их нет).
- Журнал удалений — персональные данные (UUID ученика): хранится, пока хранятся копии.
